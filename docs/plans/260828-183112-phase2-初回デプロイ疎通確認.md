# Phase 2: 初回デプロイ・本番運用の疎通確認

## Context

Phase 1（「店」タイプ検索の一気通貫フロー）はローカル（`wrangler dev`）で動作確認済み（docs/plans/260828-163014-phase1-店タイプ検索実装.md）。docs/roadmap.mdの合意通り、新機能に着手する前に、実際のCloudflare本番環境・実際のドメイン・実機で一度通しの動作を確認し、後続フェーズでの手戻りリスクを下げる。

## DoD（完了条件）

1. `MAPTILER_API_KEY`が本番Workersのシークレットとして設定されている
2. `wrangler deploy`が成功し、本番URL（`*.workers.dev`）が確定する
3. MapTilerのAPIキー設定「Allowed HTTP Origins」に本番URLが追加されている
4. 本番URLで `/api/health`, `/api/config` が正しく応答する
5. 実機（スマートフォン等）で本番URLにアクセスし、Phase 1のDoDと同じ一連の流れ（条件設定→GPS取得→検索→地図表示→再抽選→ナビ用情報コピー）が動作する

## 目的・新規リソース・コスト一覧

| 手順 | 目的 | 新規/既存リソース | コスト・注意点 |

| 2/5. KVの実利用開始 | 検索結果キャッシュを本番で使う | **新規作成ではない**。Phase 1で作成済みのKV namespace「CACHE」（id: `a0a886d9b6714920b88f9fde7bbe431a`）を初めて本番から読み書きする | 無料枠内（読取10万/日・書込1,000/日等）。これまでの`wrangler dev`テストはローカルの模擬KVを使っており、本物の無料枠は消費していない。**デプロイ後の実機確認が、実際の無料枠を消費し始める最初のタイミング** |

まとめ: 新たに「作られる」ものはCloudflare Worker本体の初回登録（＝公開URLの発行）だけである。KV・MapTilerキーはPhase 1で作成済みのものを本番から使い始めるだけで、新規発行・新規契約は発生しない。すべて無料枠内に収まる想定。

## 手順

1. **（私が実行）本番シークレット設定**: `.dev.vars`にある`MAPTILER_API_KEY`の値を使い、`npx wrangler secret put MAPTILER_API_KEY`に標準入力で渡して設定する。値そのものはチャット上に出力しない
2. **（私が実行）初回デプロイ**: `npx wrangler deploy`を実行する
   - `wrangler.jsonc`の`compatibility_date`（現在`2026-08-28`）がCloudflare側の実際の日時に対して有効か確認する。エラーが出た場合は妥当な日付に修正して再実行する
   - 出力される本番URL（`https://touring-gacha.<アカウントのworkers.devサブドメイン>.workers.dev`）を記録する
3. **（私が実行）疎通確認**: 本番URLに対しcurlで`/api/health`・`/api/config`が正しく応答することを確認する
4. **（ユーザーに依頼）MapTiler設定更新**: 取得した本番URLを、MapTiler CloudのAPIキー設定「Allowed HTTP Origins」に追加していただく（形式はローカルの`localhost`登録時と同様、スキーム・ポートなしのホスト名のみ）
5. **（ユーザーに依頼）実機確認**: スマートフォン等の実機で本番URLにアクセスし、Phase 1の一連の流れが動作するか確認していただく。結果（成功/失敗、問題があれば内容）を教えていただく
6. **（私が実行）記録**: 確認が取れたら、docs/decisions/260828-infra-cloudflare-kv.mdの残タスク（MAPTILER_API_KEYの本番シークレット設定）にチェックを入れ、本ファイルに実行結果を追記する

## リスク・注意点

- `wrangler deploy`により、touring-gachaが実際にインターネット上のURL（推測しづらいランダム性はないが、非公開リンクという扱い）で公開状態になる。個人利用前提だが、認証などのアクセス制御は現状ないため、URLを知っていれば誰でもアクセスできる状態になることは認識しておく
- KV namespace（本番用、id: `a0a886d9b6714920b88f9fde7bbe431a`）はPhase 1で作成済みのため、追加のnamespace作成は不要
- Overpass APIへの本番からのアクセスも、Phase 1と同じfair-use方針（User-Agent識別、KVキャッシュ前提）が適用される。デプロイ後の実機確認で新たなOverpassリクエストが発生する

### 手順1（シークレット設定）試行 → ブロッカー発生

`grep '^MAPTILER_API_KEY=' .dev.vars | cut -d= -f2- | npx wrangler secret put MAPTILER_API_KEY` を実行したところ、以下のエラーで失敗した。

```

🤖 Using fallback value in non-interactive context: yes
🌀 Creating new Worker "touring-gacha"...

X [ERROR] A request to the Cloudflare API (/accounts/9dd3ab40a020ce67da0cbc2f02565de7/workers/scripts/touring-gacha) failed.
```

### 手順5（実機確認）→ Overpassレート制限により候補表示まで到達できず

ユーザーが手順4（MapTiler Allowed HTTP Origins更新）を実施後、実機（iPhone/Chrome、docomo回線、大分県別府市付近からのアクセス）で本番URLにアクセス。

1. 初回アクセス: 画面は表示されたが、Chromeの位置情報許可がオフになっており「取得できませんでした」表示、検索ボタンは無効のまま → **想定通りの挙動**（GPS取得失敗時のエラーハンドリングが実機でも正しく動作したことを確認）
2. 位置情報許可をオンにして再アクセス: 現在地取得成功、検索ボタン有効化、押下で結果画面（地図・現在地中心表示）に遷移 → ここまでは正常
3. 検索結果: 「検索中…」の後「混み合っています。しばらくしてからお試しください。」（503相当のエラーメッセージ）が表示される
4. Overpassの現在の状態をcurlで簡易テスト（`node(1)`取得のみ） → HTTP 200、一見正常に見えた
5. ユーザーに再試行を依頼し、`npx wrangler tail --format json`で本番Workerのログをリアルタイム監視しながら実機で再試行してもらった。結果:

```
event.request.url: https://touring-gacha.redgem.workers.dev/api/destinations/search
event.response.status: 503
wallTime: 4773 (約4.8秒)
```

**分析**: これまでローカル環境で確認できた「Overpass検索が実際に成功したケース」は、いずれも応答時間12〜25秒程度だった（大量データの取得・処理に時間がかかるため）。今回の4.8秒という短時間での503は、Overpassが即座に拒否する「レート制限」に典型的なパターンであり、コード側の不具合ではなく、本日のセッション全体（Overpass QL構文の検証、原因調査のための複数回のデバッグクエリ、Playwrightによる自動テストの複数回実行、実機での複数回リトライ）によるOverpassサーバーへの累積負荷が原因と判断する。単発の`node(1)`テストクエリが200を返したのは、そのクエリ自体が極めて軽量なため、レート制限下でも通った可能性がある（Overpassのレート制限はクエリのコストに応じて適用される場合があるため）。

**対応**: これ以上のリトライはOverpassの利用ポリシー（fair use）に反する恐れがあるため、いったん間隔を空けることとし、本日はこれ以上の実機リトライを行わない。DoD項目5（実機での一連の流れの動作確認）は、GPS取得・検索リクエスト送信・エラー時のUI表示までは実機で確認できたが、**候補表示まで到達した実機確認はまだ完了していない**。後日あらためて確認する。

**状態**: 手順4完了。手順5は部分完了（GPS取得・検索実行・エラー時UI表示は確認済み、候補表示は未確認。Overpassのレート制限解消後に再確認予定）。

**再開までの目安**: 本番アクセスはCloudflare Workers側からOverpassへ問い合わせるため、リクエスト元IPはCloudflareの共有出口IP帯であり、他利用者の影響も受けうる。確信は持てないが、目安として30分〜1時間程度の間隔を空けてから再確認することを提案する（本日ローカル開発機からの503は45秒程度で解消した実績はあるが、今回は状況が異なるため参考程度）。

### 一晩空けて再確認 → 状況変わらず。原因の見立てを訂正

2026-08-29、ユーザーが一晩（約12時間以上）空けて実機で再試行。結果: 「検索中…」から「混み合っています。」に変わるまでの時間が5〜9秒に変化した以外、症状は変わらず（引き続き503）。

一晩経過しても解消しないことから、「本日のセッションでの負荷蓄積によるレート制限」という当初の見立てを疑い、追加診断を実施した。

**診断1**: 私の開発機（本番Workerとは別のIPアドレス）から、単純な疎通テストクエリを送信 → HTTP 200、4.5秒

**診断2**: 私の開発機から、実際の条件に近いクエリ（緯度33.27945・経度131.49751＝別府市付近、半径50km、食事・休憩カテゴリ）を送信 → **HTTP 200、9.6秒で正常に成功**。高速道路データ（「佐伯弥生バイパス」等）を含む妥当な結果が返った

**分析（見立ての訂正）**: Overpass自体は正常に稼働しており、クエリの内容にも問題がない。それにもかかわらず本番Worker（Cloudflare経由）からの同条件のリクエストだけが503で失敗し続けている。これは「touring-gachaが生成した負荷によるレート制限」ではなく、**Cloudflare Workersの共有送信元IPアドレス帯が、Overpass側で（他のCloudflare Workers利用者の行為も含め）ブロック・制限されている可能性**が高いと見立てを訂正する。Web検索でも、Cloudflare Workersの共有出口IPが外部サービス側で一括してブロックされる事例が一般的に報告されている（[Cloudflare Community](https://community.cloudflare.com/t/my-servers-ip-is-being-blocked-by-the-workers/669305), [同上](https://community.cloudflare.com/t/403-forbidden-when-calling-http-request-of-your-external-service/352717)）。

この見立てが正しい場合、時間を置くだけでは解消しない可能性がある。次の対応（別のOverpass公開インスタンスへの切り替え検討等）は設計判断を要するため、ユーザーと相談の上で別途計画する。

**状態**: 手順5はブロック継続中。原因はOverpassのレート制限ではなく、Cloudflare Workers共有IPの制限の可能性が高いと判明（未確定、要追加調査）。
