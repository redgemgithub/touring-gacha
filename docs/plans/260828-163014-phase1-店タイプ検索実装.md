# touring-gacha Phase 1実装: 計画・実行の完全記録

## この記録についての注記（2026-08-28 事後追記）

本来、CLAUDE.mdの運用ルール（計画を書き出し、実行し、結果を記録する）に加えて、規模の大小に関わらず「計画を立て→記録し→実行承認（平文での明示的な問いかけと回答）を経て→実行する」という手順を踏むべきだった。しかし本実装（Phase 1）は、Claude CodeのPlan Mode機能（`ExitPlanMode`）による内部承認のみを経て、チャット上で平文の実行承認を得ないまま着手してしまった。さらに、実装完了時に本ファイルへ記録した内容も要約されたものであり、承認プロセスを経ていない以上、要約や省略があると内容の妥当性を確認・質問することもできない。

そのため、以下を目的として本ファイルを全面的に書き直す。

1. 実際に承認された（とされた）計画の全文を、省略せずここに記録する
2. 実際に行った作業を、ファイル単位・時系列で、どの段階で何をどこまで実装したか、その順序にした理由とともに記録する
3. 計画通りに進んだ部分はそのまま記録し、計画から変更・訂正した部分は最後の「変更履歴・エビデンス」に一つ一つ、証拠となる事実（コマンド出力・エラー内容・数値）とともに記録する

コード（`src/`, `public/`）は本記録作成にあたり一切変更していない。

## 承認された計画（全文）

以下は、Claude CodeのPlan Modeで`ExitPlanMode`を呼んだ際に提示された計画の全文である（要約せず、当時の内容をそのまま再掲する）。

> # touring-gacha Phase 1実装計画: 「店」タイプの一気通貫フロー
>
> ## Context
>
> 準備段階（Cloudflareアカウント・wrangler・技術選定・MapTilerキー・Overpass利用制限の把握）が完了し（docs/decisions/260828-infra-cloudflare-kv.md）、プロジェクト雛形（Hono + Workers Static Assets、KVバインディング未設定）も動作確認済み。ここから実際の機能実装に入る。
>
> touring-gachaは目的地種別「店」「店以外」を切り替えられる仕様だが、「店以外」は交差点・行き止まり判定という新規性の高い道路トポロジー処理が必要になる。先にOverpass連携・KVキャッシュ・地図表示という基盤を、実在POIノードを検索するだけで済む「店」タイプ（食事・休憩／買い物・その他）でシンプルに動かし、基盤が固まってから「店以外」に着手する。
>
> ## Phase 1の完了条件（DoD）
>
> 1. 条件設定画面で現在地（GPS取得）・探索範囲（10/30/50/100km）・目的地種別（店＞食事・休憩／買い物・その他）を選び「目的地をさがす」を押すと、Overpass経由で候補が取得され、ランダムに1件が地図上に表示される
> 2. 下部シートに候補の名称・緯度経度・現在地からの距離と方角が出る
> 3. 「別の場所」（再抽選）で、Overpassへの新規リクエストなしに別候補へ切り替わる（クライアント側で既出候補IDを保持し、キャッシュ済み候補リストから選び直す）
> 4. 「ナビ用情報」ボタンでモーダルが独立して開き、緯度経度・名称・（取得できれば）住所を個別／一括コピーできる（要件6どおり、「決める」を押さなくても随時コピーできる。モックアップの3ボタン構成に合わせる）
> 5. 「この場所に決める」は決定状態を示すUI操作とする（例: 決定後は視覚的に確定表示にする程度。バックエンドの新規ロジックは不要）
> 6. 高速道路・高規格道路（motorway/trunk系）から100m以内の候補が除外されている
> 7. `npm run typecheck` が通り、`wrangler dev` で1〜6の一連の流れを手動確認できる
>
> **今回スコープ外**（次フェーズ以降）: 周辺情報展開画面（POI一覧・地図フォーカス連動）、目的地種別「店以外」、停車できる場所の条件
>
> ## 技術設計
>
> ### Overpass QLクエリ（`src/lib/overpass.ts`）
>
> - 「食事・休憩」: `amenity` が `restaurant/cafe/fast_food/bar/pub/ice_cream/food_court/biergarten` のいずれか
> - 「買い物・その他」: `shop=*`（全種別） + `amenity=marketplace` + `amenity=fuel`（ツーリングでの給油需要を考慮して含める。定数化しておき、後で外しやすくする）
> - 高速道路100m除外はOverpass QL側で完結させる（`around` フィルタで高速道路セットとの近接除外）。**具体的な構文（`nwr.cand(around.hw:100)` 等）は実装前に Overpass Turbo で動作検証してから組み込む**（このクラスの近接除外イディオムは構文差異が出やすいため）
> - 高速道路検索半径は候補検索半径+200mのバッファを持たせ、探索円境界付近の取りこぼしを防ぐ
> - `out center tags 300;` で要素数上限を設け、ペイロードと再抽選用データ量を制御
> - リクエストヘッダーに `User-Agent: touring-gacha/0.1 (personal use)` を付与（識別必須のfair use要件）
> - **429/5xx時、Worker内でのリトライは行わない**（Workersの実行時間制約を考慮）。1回のみ試行し、失敗時は503 + Retry-Afterをクライアントへ返す。クライアント側で「しばらく待って再試行してください」を表示する
> - 検討したが見送り: KVベースの「直前リクエストから最低N秒空ける」排他ロック。個人利用の単一ユーザーかつ検索ボタンをfetch中は無効化するUI側ガードで十分であり、KV書き込みを余計に消費してまで実装する必要性は低いと判断
>
> ### KVキャッシュと再抽選（`src/lib/cache.ts`, `src/lib/geo.ts`）
>
> - 生の緯度経度は探索半径に応じたグリッド（`radiusKm/4`）に丸めてから、Overpassクエリ中心・キャッシュキー双方に使う（キャッシュヒット率確保。表示用の距離・方角は常にユーザーの実座標から計算するため精度に影響しない）
> - キー: `ov:v1:{category}:{radiusKm}:{bucketLat}:{bucketLon}`、値: フィルタ済み`Candidate[]`、TTL 24時間
> - 再抽選はサーバーにセッション状態を持たせない。`POST /api/destinations/search` を初回・再抽選共通のエンドポイントとし、クライアントが保持する`excludeIds`をリクエストボディに含める。KVヒット時はOverpassを一切呼ばずキャッシュ済みリストから`excludeIds`を除いてランダム選出する
>
> ### ファイル構成
>

>   types.ts                # Env, Candidate, リクエスト/レスポンス型

>
> public/
>   index.html             # 1枚。view切替はdata属性+JSで行う
>   styles.css
>   js/
>     app.js                # エントリポイント、store初期化、view切替
>     state.js              # 依存ライブラリなしの最小pub/subストア
>     api.js                # fetch()ラッパー

>     views/

>
> MapLibre GL JSはCDNのUMD scriptタグ、地図スタイルは `https://api.maptiler.com/maps/streets-v2/style.json?key={key}`。キーは`GET /api/config`からクライアントへ渡す（MapTilerキーはAllowed HTTP Originsで保護される前提のクライアント向けキーであり、この受け渡しは問題ない）。ルート表現は実道路ルーティングをせず、モックアップどおり現在地→候補の直線破線（GeoJSON LineString + `line-dasharray`）。
>

## 実行結果（ファイル単位・時系列、順序の理由つき）

以下は実際に行った作業を、実行した順に記録したものである。計画通りに進んだ箇所は簡潔に、計画から変更・訂正した箇所は末尾の「変更履歴・エビデンス」で個別に詳述する（本文では該当箇所に [変更1] のように参照番号を付す）。

### A. KV・型セットアップ（計画ステップ1に対応）

1. `npx wrangler kv namespace create CACHE` を実行し、本番用KV namespace（id: `a0a886d9b6714920b88f9fde7bbe431a`）を作成
2. `npx wrangler kv namespace create CACHE --preview` を実行し、ローカル開発用のpreview namespace（preview_id: `39aa33af925f4526845ed3baa6a0ced8`）を作成
3. `wrangler.jsonc` に `kv_namespaces` ブロックを追記（上記2つのIDを設定）
4. `src/types.ts` を新規作成。`Env`（`CACHE: KVNamespace`, `MAPTILER_API_KEY: string`）、`ShopCategory`、`Candidate`、`SearchRequestBody`、`SearchResponseBody` の各型を定義
5. `npm run typecheck` 実行 → エラーなし
6. `wrangler dev` を起動し、`env.CACHE`（KV Namespace, local）と `env.MAPTILER_API_KEY`（Environment Variable, local, `.dev.vars`から読込）がバインディングとして認識されていることをログで確認、`/api/health` が引き続き `{"status":"ok"}` を返すことを確認。サーバー停止

順序の理由: KVバインディングと型定義は他の全てのバックエンドコードが依存する土台であるため、計画通り最初に行った。

### B. 純粋関数（計画ステップ2に対応）

7. `src/lib/geo.ts` を新規作成。この時点では計画通り `haversineDistanceKm`, `bearingLabel`, `bucketCoordinate` の3関数のみ実装
8. `npm run typecheck` 実行 → エラーなし

順序の理由: 外部依存のない純粋関数から先に実装し、後続のOverpassクエリ・キャッシュキー生成で使えるようにするため（計画通り）。

### C. Overpassクエリ第1版の実装と、実地検証で発覚した重大な問題

9. `src/lib/overpass.ts` を新規作成。**この時点では計画通り、高速道路100m除外をOverpass QL側の`around`近接フィルタで完結させる設計**（`nwr.cand(around.hw:100)` による集合差分）で実装した
10. 組み込み前の構文検証として、curlで実際のOverpass APIに対し1回テストクエリを送信し、HTTP 200・想定件数（300件、上限キャップ到達）が返ることを確認 [変更8: 検証手段をOverpass Turboからcurl直接検証に変更]
11. `npm run typecheck` 実行 → エラーなし
12. `src/lib/candidate.ts` を新規作成（Overpass要素→Candidate変換、住所組み立て）
13. `npm run typecheck` 実行 → エラーなし。あわせて、手順10で取得した実データに対し、変換ロジック相当の簡易スクリプトで動作確認（300件中50件で住所取得を確認）
14. `src/lib/cache.ts` を新規作成（`buildCacheKey`, `getCachedCandidates`, `putCachedCandidates`）
15. `npm run typecheck` 実行 → エラーなし
16. `src/routes/destinations.ts` を新規作成（POST /api/destinations/search。この時点では`toCandidates`の結果をそのままキャッシュ・返却する実装で、高速道路除外はOverpassクエリ内で完結している前提）
17. `src/routes/config.ts` を新規作成（GET /api/config）
18. `src/index.ts` を更新し、上記2ルートをmount
19. `npm run typecheck` 実行 → エラーなし
20. `wrangler dev` を起動し、実際に検索エンドポイントをcurlで検証:
    - `GET /api/config` → 200、MapTilerキーが返る
    - `POST /api/destinations/search`（食事・休憩、半径10km、東京駅付近） → 200、`cacheHit:false`、25.5秒。候補1件を取得できた
    - 同条件で2回目（`excludeIds`付き） → 200、`cacheHit:true`、0.06秒。別候補が返り、再抽選が機能することを確認
    - `POST /api/destinations/search`（買い物・その他、同条件） → **`candidates: []`（0件）という不審な結果**

    **この0件という結果は、この時点では「たまたま近くに買い物カテゴリの候補がなかった」ようにも見えたが、東京駅付近という立地からして不自然であり、詳細調査を行った → [変更1] に続く**

順序の理由: 計画通り、Overpass連携→候補変換→キャッシュ→ルーティングの順に、下位モジュールから積み上げて実装した。この順序自体は計画通りだが、手順20での実地検証（計画のステップ3・6で指定されていた検証）で、後述の重大な設計上の問題が発覚した。

### [変更1] 高速道路100m除外の実現方式を、Overpass側の近接結合から、アプリ側の幾何計算に変更

**計画の内容**: 「高速道路100m除外はOverpass QL側で完結させる（`around`フィルタで高速道路セットとの近接除外）」「具体的な構文は実装前にOverpass Turboで動作検証してから組み込む」

**発覚の経緯・証拠**:
1. 実装直後の単発テスト（半径2km、食事・休憩カテゴリ）ではHTTP 200・正常応答を確認し、構文自体は妥当と判断して組み込んだ
2. しかし実際のAPIルート経由での検証（半径10km、買い物・その他カテゴリ＝`shop=*`で件数の多いカテゴリ）で `candidates: []` という不審な結果が返った
3. 原因調査のため、同一クエリを直接curlで再現したところ、HTTP応答は200だが本文に `"remark": "runtime error: Query timed out in \"query\" at line 1 after 37 seconds."` が含まれており、Overpassサーバー側でクエリがタイムアウトし、空の`elements`が返っていたことが判明した
4. コードは`remark`フィールドを見ておらず、空配列を「該当候補なし」として正常にキャッシュしてしまう欠陥があった
5. 切り分けのため、(a) 高速道路除外なしの`shop=*`単体クエリ（4.7秒、300件取得）、(b) 候補検索なしの高速道路ジオメトリ単体クエリ（`out geom`、19.7秒、500件）をそれぞれ単独でcurl検証し、どちらも単独では実用的な時間で完了することを確認した。これにより、コストの高い部分は「候補集合と高速道路集合の間の近接結合（`around.hw`によるフィルタ）」そのものであると特定した

**変更内容**:
- `src/lib/overpass.ts`の`buildOverpassQuery`を書き換え、候補検索（`out center tags 300;`）と高速道路ジオメトリ取得（`out geom 200;`）を独立した2つのOverpass文にした（近接結合は行わない）
- `src/lib/geo.ts`に`distanceToSegmentMeters`（点と線分の最短距離、等距円筒図法による近似）、`distanceToPolylineMeters`（点と折れ線の最短距離）を追加

### [変更4] CSSの`.modal { display: flex }`が`hidden`属性を上書きしていた不具合の修正

**計画にない事項**（計画は実装の細部までは規定していなかったが、結果として当初のCSS実装に欠陥があった）

**発覚の経緯・証拠**: Playwrightで検索ボタンをクリックしようとしたところ、30秒のタイムアウトで失敗。Playwrightのログに「`<div hidden="" class="copy-row" id="copy-address-row">…</div>` from `<div hidden="" class="modal" id="copy-modal">…</div>` subtree intercepts pointer events」と出力されており、`hidden`属性が付いているはずのコピーモーダルが実際には表示され、クリックを妨害していることが分かった。原因は、CSSの`.modal { display: flex; }`という作者スタイルシートのルールが、`hidden`属性に対するUAスタイルシートの`display: none`より優先されるため。

**変更内容**: `public/styles.css`に`.modal[hidden] { display: none; }`を追加。
