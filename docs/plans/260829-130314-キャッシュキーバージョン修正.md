# キャッシュキーのバージョン修正（帯検索の古いキャッシュ無効化）

## Context

探索範囲の帯検索修正時にKVキャッシュのキーバージョンを上げ忘れたため、修正前（円内検索）のロジックが書き込んだ古いキャッシュが本番で読まれ続け、「50km指定なのに6.3km先が提示される」という不具合が発生した。原因・一般原則は[docs/decisions/260829-cache-key-versioning.md](../decisions/260829-cache-key-versioning.md)に記録済み。本計画はその是正を行う。

## DoD（完了条件）

1. `buildCacheKey`が生成するキーのバージョンが`v1`から`v2`に変わり、古い`ov:v1:...`キーとは別名前空間になる
2. 本番KVに残っている古い`ov:v1:...`エントリを削除する
3. 本番で該当条件（50km等）を検索した際、帯（指定距離±マージン）に収まる候補のみが返ることを実機相当（curl）で確認できる
4. `npm run typecheck`が通る

## 技術設計

- `src/lib/cache.ts`の`buildCacheKey`内、`ov:v1:` → `ov:v2:` に変更
- `buildNearbyCacheKey`（`poi:v1:`）は対象のロジック変更がないため、今回はバージョンを上げない（対象範囲外）
- 本番KVの`ov:v1:...`エントリは、バージョンを上げた時点で新しいコードから二度と参照されなくなる（自然に無害化）が、ストレージ節約のため明示的に削除もする

## 実装ステップ順序

1. `src/lib/cache.ts`の`buildCacheKey`のバージョンを`v2`に変更 → `npm run typecheck`
2. `wrangler dev`でローカル動作確認（新しいキー`ov:v2:...`でキャッシュが作られること）
3. 本番デプロイ
4. 本番KVの`ov:v1:...`エントリを`wrangler kv key delete`で削除
5. 本番で50km検索をcurl相当で1回実行し、候補が帯（45〜55km）に収まることを確認（Overpassへの実リクエストが発生するため1回に留める）
6. `docs/plans/`に実行結果を記録

## リスク・注意点

- バージョンを上げることで、既存の全キャッシュ（`ov:v1:...`）が実質的に破棄される。次回検索時にキャッシュミスとなりOverpassへの新規リクエストが発生するが、影響は軽微（個人利用規模、KV無料枠に対しても無視できる程度）
- 検証のためのOverpassへの実リクエストは1回に留める（外部APIレート制限budgeting方針）

## 実行結果

計画通りステップ1〜6を実施した。

- ステップ1（`buildCacheKey`のバージョンを`v2`に変更） → `npm run typecheck`エラーなし
- ステップ2（`wrangler dev`でのローカル確認） → `/prepare`が`"cacheKey":"ov:v2:food_rest:50:35.6982:139.7473"`を返すことを確認
- ステップ3（本番デプロイ） → 成功
- ステップ4（本番KVの古いキャッシュ削除） → `ov:v1:food_rest:50:33.2207:131.6685`を削除。削除後の一覧に`ov:v1:`が残っていないことを確認（`poi:v1:...`のみ残存、こちらは対象外のため問題なし）
- ステップ5（本番での帯フィルタ最終確認） → 本番`/prepare`（50km） → Overpassへ実際に1回リクエスト（外部APIレート制限budgeting方針に従い最小限） → `/process`で最終結果を取得。**返ってきた25件の候補すべてを機械的に検証し、全件が45〜55kmの帯に収まっていることを確認**（最小45.02km、最大49.88km、範囲外0件）。pickedも45.12kmで帯内
