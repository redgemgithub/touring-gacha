# Phase 4-A: 目的地種別「店以外」（タグ付き地点）＋停車できる場所条件

## Context

Phase 1〜3で「店」タイプの一気通貫フロー・本番運用・周辺情報表示が完成した。残る要件は「店以外」の目的地種別（要件4.2）と、探索範囲・高速道路除外まわりの基本条件（要件3）の完全な充足。

要件3「少なくとも交差点など、地点として区別できる場所を候補とする」の"交差点"検出（道路網の次数計算）は、Overpass側で行うと計算コストが非常に高い（Phase 1で`around.SET`近接フィルタが実際にタイムアウトした前例と同種のリスク）。事前調査の結果、交差点検出はデータ量・応答時間の見積もりが取れておらず、実装前に必ずスパイク検証が必要と判断した。

そのため、Phase 4を2段階に分ける。
- **Phase 4-A（今回実装）**: 峠・展望・山頂といった、Overpassのタグ検索だけで完結する「地点として区別できる場所」＋停車できる場所条件。これは店舗POIと同じ理由で交差点判定なしに要件3を満たせる
- **Phase 4-B（今回は設計のみ、実装しない）**: 次数ベースの交差点検出。スパイク（curlでの件数・応答時間計測）を行い、実用的な待ち時間に収まるか確認してから、着手可否をあらためて相談する

モックアップの「店以外」の例示「峠・展望・道の分岐 等」のうち、「道の分岐」（＝交差点）はPhase 4-Bに送る。Phase 4-Aでは峠・展望・山頂のみを扱う。

## 要件解釈の確認済み事項

- 「停車できる場所が必要」を選んだ際、候補近くに駐車場データが単に見つからない（判断できない）場合は、**その候補を除外する**（ユーザー確認済み）。「地図データから判断できる場合のみ条件として使用する」を、"判断できないものは通す"ではなく"確実に確認できたものだけ残す"と解釈する。既存の帯検索の設計思想（見つからなければ無理にひねり出さず正直に伝える）と一貫させる

## 技術設計

### 型リネーム: `ShopCategory` → `DestinationCategory`
値に`"other"`を追加。呼び出し箇所（`overpass.ts`, `candidate.ts`, `cache.ts`, `destinations.ts`）は型名の置換のみ。

### Overpassクエリ拡張（`src/lib/overpass.ts`）
- `CATEGORY_TAG_FILTERS.other`: `natural=peak`（山頂）, `natural=saddle`と`mountain_pass=yes`（峠、地域によるタグ付け慣習の違いに対応するため両方）, `tourism=viewpoint`（展望）
- 停車場所データ（`amenity=parking`, `amenity=motorcycle_parking`）は、既存の高速道路ジオメトリ取得と同じ「別のOverpass文として同一クエリ内に含める」パターンで取得する（候補との近接判定はOverpass側でやらない。高速道路除外の教訓を踏襲）。`category==="other"`のときだけクエリに追記され、既存カテゴリ（`food_rest`/`shopping_other`）のクエリ文字列・キャッシュキーは1バイトも変わらない

### 停車場所フィルタ（`src/lib/parking-filter.ts`、新規）
`isParkingElement(el)`, `filterByNearbyParking(candidates, parkingElements, bufferM)`。近接判定はアプリ側（Workers）で`haversineDistanceKm`により行う。バッファは`PARKING_PROXIMITY_BUFFER_M = 1000`（1km。実装中に実データ検証を行い、当初の暫定値50mから変更した。詳細は「実装中に判明した設計変更」参照）

### 周辺情報（Phase 3）と停車場所条件の整合性確保

「停車できる場所が必要」で選ばれた目的地は、判定に使ったのと同じ1km圏内のどこかに駐車場があることが根拠になっている。一方、既存の周辺情報表示（`src/lib/nearby.ts`、`NEARBY_POI_RADIUS_M=500m`）は駐車場も含めて一律500m圏内しか検索しない。このままだと、判定根拠の駐車場が500m〜1kmの位置にあった場合、周辺情報を開いても駐車場が1件も表示されず「該当なし」に見えてしまい、選定根拠と表示が矛盾する。

**対応**: 周辺情報一覧はもともと距離の近い順に並べて上位`NEARBY_POI_LIMIT`件のみ表示する仕組み（`rankNearbyPois`）のため、駐車場だけ検索範囲を最初から1kmにしておけば、500m以内にあれば自然と上位に、なければ500m〜1kmのものが代わりに表示される。「500mで空なら1kmに広げる」という条件分岐は不要（近い順ソート+上限件数のしくみで自然に実現できるため、あえて2段階の処理にすると複雑さとOverpassへの問い合わせ回数が増えるだけで結果は変わらない）。

- `src/lib/nearby.ts`: `buildNearbyQuery`に、駐車場だけ別半径（1km）で検索する分岐を追加する。該当しない場合（`parkingWideSearch`が偽）は既存のクエリ文字列と完全に同一のまま、既存動作への影響はない
- `src/types.ts`: `NearbyPrepareRequestBody`/`NearbyProcessRequestBody`に`parkingWideSearch?: boolean`を追加する（クライアントが任意の半径を指定できるとキャッシュキー空間が荒れるため、サーバー側の固定定数を使うON/OFFのフラグのみ渡す）
- `src/lib/cache.ts`: `buildNearbyCacheKey`に、`parkingWideSearch`が真のときだけ区別用セグメントを付与する（該当しない既存のキャッシュキーは1バイトも変えないため、`poi:v1`のバージョンは据え置きでよい）
- `public/js/nearby.js`: `picked.category === "other" && parkingRequired`のときのみ`parkingWideSearch: true`を送る

### `src/routes/destinations.ts`
`process`ハンドラで要素を「高速道路ジオメトリ／駐車場／候補」の3種に分類。`category==="other" && parkingRequired`のときのみ`filterByNearbyParking`を適用。`ALLOWED_CATEGORIES`に`"other"`追加、バリデーションに`parkingRequired: boolean`追加

### `src/lib/cache.ts`
`buildCacheKey`に`parkingRequired`引数を追加。`category==="other"`のときだけキーに区別用セグメントを付与し、既存カテゴリのキー文字列は変えない（バージョンは`v2`のまま据え置きでよい理由をコメントに明記）

### フロントエンド
- `public/index.html`: 「目的地の種類」を「店」／「店以外」の2択chip-groupに変更。「店」選択時のみ既存の食事・休憩／買い物・その他chip-groupを表示。「店以外」選択時のみ「停車できる場所」（必要／問わない）chip-groupを表示（モックアップ準拠）
- `public/js/app.js`: store初期状態に`destinationType`, `lastShopCategory`, `parkingRequired`を追加
- `public/js/views/condition.js`: 種別切り替え・表示切り替え・停車場所チップのハンドラを追加
- `public/js/api.js` / `search.js`: リクエストに`parkingRequired`を追加するのみ
- `result.js`, `map.js`, `copy-preference.js`, `nearby.js`は`Candidate`の形にのみ依存しており無改修（実装時に`grep`でカテゴリのハードコード分岐がないことを再確認する）

## 実装ステップ順序

1. `src/types.ts`型リネーム＋`parkingRequired`追加 → typecheck
2. `src/lib/overpass.ts`拡張（タグ・駐車場ブロック追加） → curlで1回実クエリを叩き、要素の混在（候補/駐車場/高速道路）を確認
3. `src/lib/parking-filter.ts`新規 → typecheck
4. `src/lib/cache.ts`拡張（`parkingRequired`をキーに反映、既存カテゴリのキーは不変であることを確認）
5. `src/routes/destinations.ts`拡張 → `wrangler dev` + curlで`parkingRequired=true/false`それぞれの候補数の違いを確認。**既存カテゴリ（食事・休憩／買い物・その他）が従来と完全に同じクエリ・キャッシュキーになることを回帰確認**
6. `public/index.html` / `app.js` / `condition.js` / `styles.css`拡張
7. `npm run typecheck`最終確認
8. 実ブラウザ（Playwright）でE2E確認: 店/店以外切り替え表示、店以外×停車場所条件での検索、高速道路100m除外が店以外でも効くこと、候補ゼロ時の既存エラー表示、を確認
9. 本番デプロイ・軽い実機/curl確認（Overpass負荷を踏まえ最小限）
10. ドキュメント更新: `docs/decisions/`に本判断（4-A/4-B分割、停車場所の「除外」解釈、タグ選定根拠）を記録。`docs/roadmap.md`・`docs/feature-map.md`を更新

## Phase 4-B（次数ベース交差点検出）は別途スパイクしてから相談

今回は実装しない。着手する場合は、curlでの件数・応答時間の事前計測（10km/30km/50km/100kmそれぞれの帯外側境界で）を行い、ユーザーが「ガチャを1回引く」体感として許容できる待ち時間（目安数秒、10秒超えは要再検討）に収まるかを見てから、あらためて計画・相談する。

## 実装中に判明した設計変更

実装ステップ2（`overpass.ts`拡張）の後、curlでの実クエリ確認に加えて、高尾山周辺（山・峠の多いエリア）で実際にOverpassへ問い合わせ、山頂・峠・展望データと駐車場データの全組み合わせで最短距離を計算する検証を行った（レート制限budgetに配慮し、1回の実クエリ結果を使い回して複数の距離しきい値を机上計算した。追加のOverpassリクエストは発生させていない）。

| 距離しきい値 | 該当候補数（300件中） |
|---|---|
| 50m（当初の暫定値） | 0件 |
| 100m | 0件 |
| 200m | 1件 |
| 300m | 1件 |
| 500m | 5件 |
| 1000m | 32件 |
| 2000m | 71件 |

店舗（建物の出入口に駐車場が隣接することが多い）と異なり、山頂・峠・展望はOSM上のタグ位置が地形の頂点そのものであり、実際の駐車場（登山口・展望駐車場等）はそこから数百m以上離れているのが一般的なため、店舗カテゴリと同じ50mバッファを流用すると「停車できる場所が必要」を選んだ場合に事実上常に候補0件になることが判明した。

ユーザーと協議の上、以下の2点を計画に追加した。
1. `PARKING_PROXIMITY_BUFFER_M`を`50m`→`1000m`に変更する。ツーリングでバイクを停める場所を探す感覚として「1km以内にあれば近くにある」とみなす、というユーザーの判断による
2. 上記の変更により、判定根拠の駐車場が既存の周辺情報表示（500m圏内）の外にあるケースが生じうるため、周辺情報表示側でも駐車場だけ1km圏内を検索するよう整合性を取る（詳細は「周辺情報（Phase 3）と停車場所条件の整合性確保」参照）
