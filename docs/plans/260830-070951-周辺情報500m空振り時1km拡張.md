# 周辺情報表示: 500mで0件のとき1kmへ1回だけ拡張検索する

## Context

Phase 4-Bの動作確認中、交差点を目的地に選んで「周辺のスポットを見る」を開いたところ、時間が掛かった上に「見つかりませんでした」となる事例に遭遇した。調査の結果、これは不具合ではなく、既存の周辺情報表示（Phase 3、`NEARBY_POI_RADIUS_M=500m`固定）が交差点に対しても同じロジックで正しく動いた結果であることを確認した（実際に別の交差点候補では500m以内に50件ヒットすることも確認済み）。

ただし、この現象自体はユーザーとの協議の結果、放置すべきでない構造的な差だと判断した。「店」は目的地自体が店であるため周辺にも店がある確率が高く、「店以外」（峠・展望・山頂）も名所として何かが近くにある場合が多いのに対し、「交差点」は道路の構造だけで選ばれるため、周辺に何もない場所に当たる確率が他のカテゴリより明らかに高い。この非対称性を緩和するため、周辺情報表示に「500mで0件なら1kmまで1回だけ拡張する」仕組みを追加する。

## 決定事項

- 対象は**全カテゴリ共通**とする（周辺情報表示自体が目的地のカテゴリに関係なく同じロジックで動いているため、交差点だけを特別扱いする理由がない。店以外（峠・展望等）でも500mで0件の場合は同様に救われる）
- 拡張は**1回だけ**（500m→1km）。1kmでも0件なら、それ以上は探さず正直に「見つかりませんでした」を返す（既存の帯検索・交差点探索と同じ「無理に見つけようとせず正直に伝える」方針を踏襲）
- 拡張の判定基準は「ランキング後の件数が0件かどうか」とする（Phase 4-Bの交差点プローブのような閾値（5件等）は設けず、単純に0件かどうかで判断する。ユーザーの要求「500mで見つからなければ」に忠実に対応する）
- 既存の駐車場ワイド検索（`parkingWideSearch`、店以外×停車場所条件のときだけ駐車場を1km圏内で検索する仕組み）とは独立した別軸の機能とする。両者が同時に有効な場合（店以外×停車場所条件×500m全体0件）、拡張時のクエリは全体を1kmにする（駐車場は元々1kmなので実質変化なし、他のPOI種別も1kmになる）

## 技術設計

### `src/lib/nearby.ts`

`NEARBY_ESCALATE_RADIUS_M = 1000`を追加する。`buildNearbyQuery`は既に`radiusM`を引数に取れる作りのため変更不要（拡張時は`buildNearbyQuery(lat, lon, NEARBY_ESCALATE_RADIUS_M, parkingWideSearch)`をそのまま呼べる）。

### API設計: prepare/processの多段階化（Phase 4-Bと同じパターン）

`src/types.ts`:
```ts
export interface NearbyPrepareRequestBody {
  lat: number;
  lon: number;
  excludeId: string;
  parkingWideSearch?: boolean;
}

export type NearbyPrepareResponseBody =
  | ({ status: "done" } & NearbyResponseBody)
  | {
      status: "need_fetch";
      query: string;
      endpoint: string;
      cacheKey: string;
      // 初回（500m）で0件だった場合のみ使用。1kmへの拡張問い合わせであることを示す
      nearbyStage?: "escalate";
    };

export interface NearbyProcessRequestBody {
  cacheKey: string;
  lat: number;
  lon: number;
  excludeId: string;
  overpassResponse: unknown;
  parkingWideSearch?: boolean;
  nearbyStage?: "escalate";
}

export type NearbyProcessResponseBody = NearbyPrepareResponseBody;
```

`src/routes/nearby.ts`の`/process`: ランキング後の件数が0件、かつ`nearbyStage !== "escalate"`（まだ拡張していない）なら、`buildNearbyQuery(lat, lon, NEARBY_ESCALATE_RADIUS_M, parkingWideSearch ?? false)`を`need_fetch`（`nearbyStage: "escalate"`）で返す。拡張後（`nearbyStage === "escalate"`）は件数に関わらずキャッシュして`done`を返す。

`public/js/nearby.js`: `search.js`と同様、`need_fetch`が続く限りfetch→processを繰り返すループにする。

`public/js/api.js`: `processNearby`に`parkingWideSearch`/`nearbyStage`を追加で渡せるようにする。

### `src/lib/cache.ts`: キャッシュバージョンを上げる

`buildNearbyCacheKey`の接頭辞を`poi:v1`→`poi:v2`に変更する。500mで0件だった場合にキャッシュする内容が変わる（従来: 0件をそのままキャッシュ／変更後: 1kmまで試してから結果をキャッシュ）ため、既存の`poi:v1:...`エントリ（拡張前ロジックでキャッシュされた0件の結果を含みうる）をそのまま使い続けるとロジック変更が反映されない。CLAUDE.mdのキャッシュキーバージョニング原則に従い、必ずバージョンを上げる。

## リスク・注意点

- 検証時のOverpassへの実リクエストは、外部APIレート制限budgeting方針に従い必要最小限に留める
