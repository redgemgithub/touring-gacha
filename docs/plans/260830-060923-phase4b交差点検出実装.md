# Phase 4-B: 次数ベースの交差点検出の実装

## Context

Phase 4-Bはスパイク検証（`docs/plans/260829-214939-phase4bスパイク検証.md`）でGOと判断済み。設計は「指定距離ちょうどの乱数点（仮地点）を1つ決め、その周辺100mで交差点数を診断（プローブ）→不足していれば1kmまで1回だけ拡張→それでも見つからなければ正直に伝える」。

その後の協議で、以下2点を確定した。

1. スパイク後に一度「本実装は保留」としたのは誤りだった。「実際に使って考える」は探索範囲・閾値等のパラメータ調整の要否についての話であり、実装するかどうかの話ではない。実装は行う
2. 交差点候補を既存の「店以外」（峠・展望・山頂）の候補プールに混ぜない。交差点は仮地点1点の周辺（±1km程度）に局所的に固まるという、峠・展望・山頂（帯全体から均等に出る）とは異質な性質を持つため、混ぜると「同じ店以外なのに実際の挙動が違う」という利用者への裏切りになる。**目的地の種類を「店」「店以外」「交差点」の3択にする**
3. 交差点には詳細条件（停車できる場所、等）を設けない。負荷が大きいとわかっている検索にさらに条件を足さない

## 決定事項

- `DestinationCategory`に`"intersection"`を追加する（`"food_rest" | "shopping_other" | "other" | "intersection"`）
- 条件設定画面の「目的地の種類」を3択chip-cardにする。表記は**「スポット（店）」「スポット（店以外）」「交差点」**とする。「店以外」の次に構造の異なる「交差点」が並ぶ違和感を避けるため、共通の括り「スポット」を用いる。「POI」という英語表記も検討したが、既存の周辺情報表示側で既に「スポット」という訳語を使っている（「周辺のスポットを見る」等）ため、アプリ内の用語を揃える意味でこちらを採用した。「交差点」選択時は、店の種類・停車できる場所のどちらの詳細フィールドも表示しない
- 次数（そのノードを共有する異なるway数）が**3以上**のノードを交差点候補とする
- 仮地点は、現在地から**乱数の方角**（0〜360°）×**指定距離ちょうど**（`radiusKm`）の点とする。既存の帯（`innerKm`〜`outerKm`）の中のどこかではなく、指定距離ちょうどにする理由: 仮地点自体が帯の内側に寄りすぎたり外側に寄りすぎたりすると、そこから半径1kmまで拡張した際に帯の外にはみ出す候補ばかりになりかねないため、帯の中心である指定距離ちょうどを基準にするのが安全
- プローブ半径100m、拡張半径1kmは固定値とする。プローブでの最小件数の閾値（何件あれば拡張せず確定してよいか）は暫定値**5件**とし、実装後に実データで妥当性を確認する（`PARKING_PROXIMITY_BUFFER_M`と同様、暫定値として扱う）
- 最終的な候補は、既存の帯フィルタ（現在地からの距離が指定の帯に収まっているか）・高速道路100m除外を、他カテゴリと同様に適用する
- キャッシュキーのバージョン（`ov:v3`）は据え置きでよい。`"intersection"`は新規のカテゴリ値であり、既存カテゴリの意味を変更するものではないため（旧バージョンのキャッシュを誤って再利用するリスクがない）

## 技術設計

### `src/lib/geo.ts`: 仮地点計算の追加

現在地から方角・距離を指定して到達点を求める関数（順方向の球面測地線計算）を追加する。

```ts
export function destinationPoint(
  lat: number,
  lon: number,
  bearingDeg: number,
  distanceKm: number,
): { lat: number; lon: number } {
  const R = EARTH_RADIUS_KM;
  const δ = distanceKm / R;
  const θ = (bearingDeg * Math.PI) / 180;
  const φ1 = (lat * Math.PI) / 180;
  const λ1 = (lon * Math.PI) / 180;
  const φ2 = Math.asin(Math.sin(φ1) * Math.cos(δ) + Math.cos(φ1) * Math.sin(δ) * Math.cos(θ));
  const λ2 =
    λ1 + Math.atan2(Math.sin(θ) * Math.sin(δ) * Math.cos(φ1), Math.cos(δ) - Math.sin(φ1) * Math.sin(φ2));
  return { lat: (φ2 * 180) / Math.PI, lon: (λ2 * 180) / Math.PI };
}
```

### `src/lib/intersection.ts`（新規）: 交差点クエリ組み立て・次数計算

```ts
export const INTERSECTION_PROBE_RADIUS_M = 100;
export const INTERSECTION_ESCALATE_RADIUS_M = 1000;
export const INTERSECTION_DEGREE_THRESHOLD = 3;
// プローブでこの件数以上あれば、拡張せずそこで確定する（暫定値）
export const INTERSECTION_PROBE_MIN_COUNT = 5;
const MAX_WAY_ELEMENTS = 20000;
const MAX_NODE_ELEMENTS = 60000;
const HIGHWAY_SEARCH_BUFFER_M = 200; // overpass.tsと同じ考え方

export function buildIntersectionQuery(anchorLat: number, anchorLon: number, radiusM: number): string {
  const highwayRegex = EXCLUDED_HIGHWAY_TYPES.join("|"); // overpass.tsからexport
  return (
    `[out:json][timeout:25];` +
    `way["highway"](around:${radiusM},${anchorLat},${anchorLon})->.roads;` +
    `.roads out body ${MAX_WAY_ELEMENTS};` +
    `(._;>;);out skel qt ${MAX_NODE_ELEMENTS};` +
    `way["highway"~"^(${highwayRegex})$"](around:${radiusM + HIGHWAY_SEARCH_BUFFER_M},${anchorLat},${anchorLon})->.hw;` +
    `.hw out geom;`
  );
}

export interface IntersectionElement {
  type: "way" | "node";
  id: number;
  nodes?: number[]; // way
  lat?: number; // node
  lon?: number; // node
  tags?: Record<string, string>;
}

export function computeIntersectionCandidates(
  elements: IntersectionElement[],
): { id: string; lat: number; lon: number }[] {
  const ways = elements.filter((el) => el.type === "way" && Array.isArray(el.nodes));
  const nodeById = new Map(
    elements.filter((el) => el.type === "node").map((el) => [el.id, el]),
  );
  const nodeToWays = new Map<number, Set<number>>();
  for (const way of ways) {
    for (const nodeId of way.nodes ?? []) {
      if (!nodeToWays.has(nodeId)) nodeToWays.set(nodeId, new Set());
      nodeToWays.get(nodeId)!.add(way.id);
    }
  }
  const candidates: { id: string; lat: number; lon: number }[] = [];
  for (const [nodeId, waySet] of nodeToWays) {
    if (waySet.size < INTERSECTION_DEGREE_THRESHOLD) continue;
    const node = nodeById.get(nodeId);
    if (!node || typeof node.lat !== "number" || typeof node.lon !== "number") continue;
    candidates.push({ id: `node/${nodeId}`, lat: node.lat, lon: node.lon });
  }
  return candidates;
}
```

- スパイクのスクリプトと同じロジック（次数≥3のノードを交差点候補とする）をそのまま製品コードに移植する
- 高速道路ジオメトリは仮地点周辺で別途取得し、既存の`excludeNearHighways`をそのまま使う（`overpass.ts`の`EXCLUDED_HIGHWAY_TYPES`をexportして共有する）
- クエリ中の`out body`/`out skel qt`にOverpassの出力上限を明示し、万一の暴走に備える（実測値を踏まえた余裕を持った値）

### API設計: prepare/processの多段階化

既存カテゴリは「prepare→（クライアントがOverpassへ直接fetch）→process」で1往復するが、交差点はプローブ→（必要なら）拡張の最大2段階になりうる。`PrepareResponseBody`の`need_fetch`側に、交差点カテゴリのときだけ使うフィールドを追加し、`/process`のレスポンス型を`PrepareResponseBody`と同じ型（doneまたはneed_fetch）にすることで、クライアント側は「`need_fetch`である限りfetch→processを繰り返す」というループ1つで両カテゴリに対応できるようにする。

```ts
// src/types.ts
export type DestinationCategory = "food_rest" | "shopping_other" | "other" | "intersection";

export type PrepareResponseBody =
  | ({ status: "done" } & SearchResponseBody)
  | {
      status: "need_fetch";
      query: string;
      endpoint: string;
      cacheKey: string;
      // "intersection"カテゴリのときのみ使用。プローブ/拡張のどちらの問い合わせかと、
      // 両段階で共有する仮地点
      intersectionStage?: "probe" | "escalate";
      anchor?: { lat: number; lon: number };
    };

// ProcessRequestBodyにも intersectionStage / anchor を追加（category==="intersection"のときのみ使用）
// ProcessResponseBody は PrepareResponseBody を再利用する（doneかneed_fetchかを返せるようにする）
```

`src/routes/destinations.ts`の処理フロー（`category === "intersection"`のとき）:

1. `/prepare`: キャッシュ確認。ヒットすれば`done`。ミスなら、`destinationPoint`で仮地点を決め、`buildIntersectionQuery(anchor, INTERSECTION_PROBE_RADIUS_M)`を`need_fetch`（`intersectionStage: "probe"`, `anchor`同梱）で返す
2. `/process`（`intersectionStage: "probe"`受領時）: `computeIntersectionCandidates`で交差点候補を計算し、高速道路除外・帯フィルタを適用。件数が`INTERSECTION_PROBE_MIN_COUNT`以上なら、そのままキャッシュして`done`を返す。不足していれば、同じ`anchor`で`buildIntersectionQuery(anchor, INTERSECTION_ESCALATE_RADIUS_M)`を`need_fetch`（`intersectionStage: "escalate"`）で返す
3. `/process`（`intersectionStage: "escalate"`受領時）: 同様に候補を計算し、件数に関わらず（0件でも）キャッシュして`done`を返す（見つからなければ正直に0件を返す。それ以上は拡張しない）
4. `pickCandidate`・KVキャッシュへの保存は既存の仕組みをそのまま使う（`Candidate.name`は基本`null`、`category: "intersection"`）

## リスク・注意点

- `INTERSECTION_PROBE_MIN_COUNT=5`は暫定値。実装後、実データで数件目視確認して妥当性を判断する
- 次数≥3を交差点とする判定は簡易的で、同一道路がタグ上複数wayに分割されているだけのケースを誤検出する可能性がある（スパイク時点で把握済みの簡略化）。実際の候補地点を目視確認し、明らかにおかしい場合は判定ロジックの見直しを検討する
- 交差点候補は仮地点1点の周辺（±1km程度）に局所的に固まる。この性質は目的地の種類を分けたことで利用者に隠さずに済んでいるが、実装時にあらためて認識しておく
- 検証時のOverpassへの実リクエストは、外部APIレート制限budgeting方針に従い必要最小限に留める
- 既存カテゴリ（店・店以外）の動作・キャッシュに影響がないことを明示的に回帰確認する

2. `overpass.ts`に`TagBasedDestinationCategory`（`Exclude<DestinationCategory, "intersection">`）を新設し、`CATEGORY_TAG_FILTERS`・`buildOverpassQuery`の型をこれに絞った（`buildOverpassQuery`に`"intersection"`を渡せないことをコンパイル時に保証するため。計画時点では明記していなかった型設計上の工夫）
3. 実装中に、Overpassの`out geom`が`nodes`と`geometry`の両方を返す仕様であることが判明し、`computeIntersectionCandidates`の道路網グラフ用way判定に`!Array.isArray(el.geometry)`条件を追加した（計画時点では想定していなかった、実データ検証で判明した修正）
