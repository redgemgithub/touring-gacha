# 交差点の仮地点が海上に当たった場合、内部で自動的に引き直す

## Context

実機確認で、交差点検索が立て続けに「見つかりませんでした」になる事例が報告された。調査の結果、仮地点の方角を`Math.random() * 360`で決めており、陸か海かを一切考慮していないことが原因と判明した。横浜（湾岸）を起点に50km・8方角で検証したところ、**8方角中2方角（25%）が海上に着地し、1kmまで拡張しても道路データが一切見つからなかった**。海沿いの都市が起点だと、方角によっては無視できない確率で海に当たる。

`is_in`（行政区画への包含判定）による軽量な陸地事前チェックを検討したが、日本の沿岸自治体は行政区画が海側にも及んでいることが多く、海上の地点も「陸地」と誤判定されることを実測で確認した。他の代替手段（海域ポリゴンでの判定等）も、外洋が明示的なポリゴンとしてタグ付けされていないことが多く、確実な軽量化は見込めなかった。

## 決定事項（ユーザー確認済み）

- 事前の陸地判定は行わない（軽量化できないため）
- 1つの仮地点が完全な空振り（プローブ100m・拡張1kmとも道路データ0件）だった場合、それを利用者に見せる前に、**内部で自動的に別の方角の仮地点を引き直す**
- 引き直しの上限は**2回**（＝仮地点は最大2つ試す。1つの仮地点あたり最大2回のOverpass問い合わせ〈プローブ＋拡張〉のため、最大4回のOverpass問い合わせになる）
- 2回とも完全な空振りだった場合のみ、これまで通り正直に「見つかりませんでした」と伝える（前回追加した「もう一度探す」ボタンで、利用者が望めばさらに引き直せる）
- 距離（`radiusKm`）は変えず方角だけ引き直すため、既存の「探索範囲を勝手に広げない」方針とは矛盾しない

## 技術設計

### `src/types.ts`

`ProcessRequestBody`・`PrepareResponseBody`の`need_fetch`側に、仮地点の試行回数を追加する。

```ts
// "intersection"カテゴリのみ使用。仮地点を何回引き直したか（1始まり）。
// 完全な空振りが続いた場合の内部リトライ上限判定に使う
anchorAttempt?: number;
```

### `src/lib/intersection.ts`

`INTERSECTION_MAX_ANCHOR_ATTEMPTS = 2`を追加する。

### `src/routes/destinations.ts`

- `/prepare`: 交差点の仮地点生成時、`anchorAttempt: 1`を付与する
- `/process`: `intersectionStage === "escalate"`の確定判定を拡張する。帯フィルタ前の`nonHighwayCandidates.length === 0`（完全な空振り）で、かつ`anchorAttempt < INTERSECTION_MAX_ANCHOR_ATTEMPTS`のときは、新しい方角で仮地点を引き直し、`intersectionStage: "probe"`・`anchorAttempt: anchorAttempt + 1`の`need_fetch`を返す。それ以外（何か見つかった、または上限に達した）は、これまで通り確定する

### `public/js/search.js` / `public/js/api.js`

多段階ループは既存の仕組み（`need_fetch`が続く限り繰り返す）でそのまま対応できるため、`anchorAttempt`を透過的に引き回すだけでよい。`prepareSearch`/`processSearch`に`anchorAttempt`を追加する。

## リスク・注意点

- 最悪時（2回とも完全空振り）は最大4回のOverpass問い合わせが直列で発生し、待ち時間が伸びる可能性がある。外部APIレート制限budgeting方針の範囲内に収まるよう、検証時のリクエスト回数は必要最小限に留める
- 上限2回でも、離島など陸地の少ない起点では引き続き空振りが起こりうる。その場合は既存の「見つかりませんでした」＋「もう一度探す」で対応する（無理に見つけようとしない、という既存方針を維持）
