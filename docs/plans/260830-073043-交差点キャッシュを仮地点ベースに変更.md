# 交差点候補のキャッシュを「現在地ベース」から「仮地点ベース」に変更

## Context

Phase 4-B実装後の実動作確認で、「トップ画面に戻って検索し直しても、その場で再抽選しても、検索結果地点がほぼ変わらない」という指摘があった。

原因はキャッシュ設計にあった。交差点候補のキャッシュキーは、現在地・探索範囲・カテゴリ（`ov:v3:intersection:...`）でバケット化されており、他カテゴリ（店・店以外）と同じ仕組みを踏襲していた。しかし他カテゴリは帯全体（数十km四方）から候補を集めるため、同じキャッシュから何度別候補を選んでも多様性があるのに対し、**交差点は候補全部が仮地点1点の周辺（最大1km程度）に集まっている**ため、同じキャッシュバケットの中でしか候補を選べず、結果的に毎回似たような地点になっていた。しかも仮地点の乱数決定はキャッシュが空のとき（最初の1回）にしか行われないため、同じ現在地・探索範囲・カテゴリでの検索は「トップからやり直す」場合も「再抽選」の場合も同じキャッシュを共有し、新しい仮地点が引かれることは実質なかった。

## 決定事項（ユーザー確認済み）

- 仮地点は検索のたび（再抽選を含む）に必ず新しく引き直す
- ただし、引き直した仮地点が過去にキャッシュ済みの領域と近ければ、そのキャッシュを再利用する（Overpassへの問い合わせを避け、レート制限に配慮する）。「キャッシュを使わない」という前回提案した対応は採用しない

## 技術設計

### キャッシュキーを仮地点ベースにする

`src/lib/cache.ts`に`buildIntersectionCacheKey(anchorLat, anchorLon)`を新設する。現在地・探索範囲・カテゴリではなく、**仮地点自身の座標**をバケット化する（`bucketCoordinate(anchorLat, anchorLon, 1)`、1km基準で250m四方のバケット）。プレフィックスは`int:v1:`とし、既存の`ov:v3:`（現在地ベース）とは別のキー空間にする。

### キャッシュに保存する内容: 帯フィルタ前のデータ

帯フィルタ（現在地から見て指定の帯に収まっているか）は現在地・探索範囲に依存するため、仮地点ベースでキャッシュしたデータをそのまま返すと、別の現在地・探索範囲からの再利用時に正しくない可能性がある。そこで、**キャッシュには高速道路除外後・帯フィルタ前の候補を保存し、キャッシュ取得後（ヒット・ミスどちらの場合も）に、そのときどきの現在地・探索範囲で帯フィルタを都度適用する**設計にする。

### `/prepare`（`src/routes/destinations.ts`）

`category === "intersection"`のとき:
1. 仮地点を引く（`destinationPoint`、毎回必ず新規）
2. `buildIntersectionCacheKey(anchor.lat, anchor.lon)`でキャッシュ確認
3. ヒットすれば、そのときの現在地・探索範囲で帯フィルタを適用し、`status: "done"`で即座に返す（Overpassへの問い合わせなし）
4. ミスならプローブクエリ（100m）を`need_fetch`で返す（従来通り）

### `/process`

`category === "intersection"`のとき:
- 高速道路除外までは従来通り
- プローブ→拡張の要否判定は、**そのときの現在地・探索範囲での帯フィルタ後の件数**で判定する（従来のロジックを維持。仮地点ベースキャッシュへの変更とは独立した判断基準のため変えない）
- 確定時、キャッシュには**帯フィルタ前**（高速道路除外後）の候補を保存する
- レスポンスには帯フィルタ後の候補を返す

## 実装ステップ順序

1. `src/lib/cache.ts`に`buildIntersectionCacheKey`を追加 → typecheck
2. `src/routes/destinations.ts`の`/prepare`・`/process`を上記設計に沿って書き換え
3. `npm run typecheck`
4. `wrangler dev` + curlで以下を確認
   - 同じ現在地・探索範囲で複数回検索/再抽選した際、毎回異なる仮地点・異なる地域の候補になること（現在の不具合の再現・修正確認）
   - 意図的に同じ仮地点付近を引かせる（テスト用に固定の仮地点でキャッシュを作った後、同じ座標でキャッシュ確認）ことでキャッシュヒットし、Overpassへの再問い合わせが発生しないこと
   - 既存カテゴリ（食事・休憩／買い物・その他／店以外）の動作・キャッシュキーに変化がないこと
5. 実ブラウザ（Playwright）で、複数回の検索・再抽選で結果地点が実際に変わることを確認
6. 本番デプロイ・軽い疎通確認
7. 本番KVに残っている旧`ov:v3:intersection:...`エントリ（今回の変更でもう読み書きされなくなる）を確認し、残っていれば削除する
8. ドキュメント更新: `docs/decisions/260830-phase4b交差点検出実装.md`に追記（当初の設計の問題点と修正内容）。`docs/plans/260830-060923-phase4b交差点検出実装.md`の該当記述（現在地ベースキャッシュの説明）にも参照を追記

## リスク・注意点

- 検証時のOverpassへの実リクエストは、外部APIレート制限budgeting方針に従い必要最小限に留める
- 帯フィルタを「キャッシュ保存前」から「キャッシュ取得後」に移すため、既存の確定ロジック（プローブ/拡張判定・キャッシュ保存タイミング）の変更箇所を注意深く確認する

## 実行結果

計画通り、ステップ1〜8をすべて実施した。

### 1〜2. コード変更

- `src/lib/cache.ts`: `buildIntersectionCacheKey(anchorLat, anchorLon)`を追加（`int:v1:...`、`bucketCoordinate(anchorLat, anchorLon, 1)`で250m四方にバケット化）
- `src/routes/destinations.ts`: `/prepare`で交差点カテゴリの分岐を、現在地ベースのキャッシュ確認より前に移動。仮地点を先に引き、仮地点ベースのキャッシュキーで確認するよう変更。キャッシュヒット時はそのときの現在地・探索範囲で帯フィルタを適用してから返す。`/process`では、確定時にキャッシュへ保存する内容を「帯フィルタ後」から「帯フィルタ前（高速道路除外後）」に変更

### 3. `npm run typecheck`

エラーなしで完了。

### 4. `wrangler dev` + curlでの動作確認

- 同一の現在地・探索範囲・カテゴリで`/prepare`を3回連続実行し、毎回異なる仮地点が返ることを確認（修正前は同一の仮地点候補群から選ぶだけだった）

- 既存カテゴリ（食事・休憩／店以外）の`/prepare`が引き続き正常に動作することを確認（キャッシュキー形式に変化なし）
