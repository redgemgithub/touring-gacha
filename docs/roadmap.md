# touring-gacha 全体計画（ロードマップ）

## この文書について

- 本来、Phase 1（「店」タイプ検索）に着手する前に作っておくべきだった、touring-gacha全体の実装フェーズ分解である。事後に作成した
- `docs/plans/` 配下の個別作業記録（`yymmdd-hhmmss-内容.md`、実行するたびに新規作成）とは異なり、本文書はフェーズの進捗に応じて更新していく文書とする
- 各フェーズの着手時には、本文書を踏まえて個別の`docs/plans/`計画ファイルを作り、実行承認（チャットでの明示的な平文の問いかけと回答）を経てから着手する
- フェーズ分解・順序は本文書作成時点での提案であり、内容の承認前は確定した計画として扱わない

## フェーズ一覧

### Phase 1: 「店」タイプ検索の一気通貫フロー — 完了（2026-08-28）

条件設定（GPS取得・探索範囲・目的地種別「店」＞食事・休憩／買い物・その他）→Overpass検索→地図表示（現在地・候補ピン・破線ルート・距離方角）→再抽選→ナビ用情報コピーモーダル、の一連のフロー。

- 対応する要件: docs/requirements.md 3(基本条件のうち高速道路除外)・4.1(店)・6(ナビ連携はコピーで十分)
- 記録: [docs/plans/260828-163014-phase1-店タイプ検索実装.md](./plans/260828-163014-phase1-店タイプ検索実装.md)（計画全文・実行結果・変更履歴を記録済み）

### Phase 2: 初回デプロイ・本番運用の疎通確認 — 完了（2026-08-29）

`wrangler secret put`によるMAPTILER_API_KEYの本番設定、初回`wrangler deploy`、本番workers.dev URLの確定、MapTilerのAllowed HTTP Originsへの本番URL追加、実機（スマートフォン等）での動作確認。

- なぜここに置くか（提案理由）: Phase 1で「店」タイプの基本機能はローカルで実際に使えるレベルまで動いている。新機能を追加する前に、一度実際のCloudflare本番環境・実際のドメイン・実機GPSで通しの動作を確認しておくことで、後続フェーズでの手戻りリスクを下げられると考えた
- 対応する要件: docs/requirements.md 2(運用環境)
- 実機確認の過程で、Cloudflare Workersの共有送信元IPがOverpass API側で制限を受けていることが判明し、Overpassへの問い合わせをサーバー側からブラウザ側の直接fetchへ変更する設計変更を行った（[docs/decisions/260829-overpass-client-side-fetch.md](./decisions/260829-overpass-client-side-fetch.md)）。この変更により実機での動作を確認できた
- 記録: [docs/plans/260828-183112-phase2-初回デプロイ疎通確認.md](./plans/260828-183112-phase2-初回デプロイ疎通確認.md)、[docs/plans/260829-082814-overpassクライアント直接fetch移行.md](./plans/260829-082814-overpassクライアント直接fetch移行.md)

### Phase 3: 周辺情報表示（周辺情報展開画面） — 完了（2026-08-29）

結果画面の下部シートを引き上げて、目的地本体＋近くのPOI一覧を表示する画面（`docs/mockups/result-expanded.png`に対応）。POI取得は目的地検索と同じprepare/process/ブラウザ直接fetchパターンを踏襲。一覧から地図上の該当ピンへフォーカスする操作を含む。

- なぜPhase 2の次か（提案理由）: Phase 1で作った基盤（Overpass連携・地図表示・状態管理）の上に、既存の枠組みを拡張するだけで実現できる機能であり、新規性の高いドメインロジック（Phase 4の交差点判定等）より先に着手する方がリスクが低いと考えた
- 対応する要件: docs/requirements.md 7(周辺情報表示)
- 実装完了後、周辺POIを選択できても情報をコピーできないという指摘を受け、コピーの仕組み自体を見直した（都度選択のモーダルから、アプリ全体で1回設定する方式へ変更。[docs/decisions/260829-copy-preference.md](./decisions/260829-copy-preference.md)）
- 本番運用で、コピー結果が空になる問題・探索範囲帯の中抜け・チェーン店名だけでは地点を特定できない問題が見つかり、Phase 4着手前に追加対応した（[docs/decisions/260829-search-radius-band-gapless.md](./decisions/260829-search-radius-band-gapless.md)、[docs/decisions/260829-copy-preference.md](./decisions/260829-copy-preference.md)の追記部分）
- 記録: [docs/plans/260829-112551-phase3-周辺情報表示.md](./plans/260829-112551-phase3-周辺情報表示.md)、[docs/plans/260829-121720-コピー項目設定と周辺POIコピー.md](./plans/260829-121720-コピー項目設定と周辺POIコピー.md)、[docs/plans/260829-191156-フィードバック対応と要件定義注意点.md](./plans/260829-191156-フィードバック対応と要件定義注意点.md)、[docs/plans/260829-193713-長押しで緯度経度強制コピー.md](./plans/260829-193713-長押しで緯度経度強制コピー.md)

### Phase 4-A: 目的地種別「店以外」（タグ付き地点）＋停車できる場所条件 — 完了（2026-08-29）

峠・展望・山頂といった、Overpassのタグ検索だけで完結する「地点として区別できる場所」（`natural=peak`・`natural=saddle`・`mountain_pass=yes`・`tourism=viewpoint`）＋停車できる場所条件（駐車場データが1km以内に見つからない候補は除外）。

- なぜPhase 4を4-A/4-Bに分けたか（提案理由）: 要件3の交差点検出（道路網の次数計算）はOverpass側の計算コストが高く、データ量・応答時間の見積もりが取れていない状態だったため、タグ検索だけで完結する部分（4-A）と交差点検出（4-B、スパイク検証が必要）を切り分けた
- 対応する要件: docs/requirements.md 4.2(店以外)。要件3(基本条件)のうち交差点検出はPhase 4-Bへ持ち越し
- 実装中、停車場所の近接判定バッファを実データで検証した結果、当初の暫定値（50m）では事実上機能しないことが判明し、1kmに変更した。これに伴い、Phase 3の周辺情報表示（500m圏内）との整合性も別途確保した
- 記録: [docs/decisions/260829-phase4a-店以外タグ地点と停車場所.md](./decisions/260829-phase4a-店以外タグ地点と停車場所.md)、[docs/plans/260829-185103-phase4a-店以外タグ地点と停車場所.md](./plans/260829-185103-phase4a-店以外タグ地点と停車場所.md)

### Phase 4-B（案）: 次数ベースの交差点検出 — スパイク検証完了（GO）・本実装は保留（2026-08-29）

要件3「少なくとも交差点など、地点として区別できる場所を候補とする」の完全な充足、直線路途中・行き止まりの除外。「店以外」のモックアップ例示のうち「道の分岐」に相当。

- スパイク検証（curlでの件数・応答時間の実測）を実施し、GOと判断した。設計は「指定距離ちょうどの乱数点（仮地点）を決め、その周辺100mで交差点数を診断→不足していれば1kmまで1回だけ拡張→それでも見つからなければ正直に伝える」。10kmまで広げる案は、データ量が数十MBに達し429（レート制限）も発生したため不採用とした
- 本実装への着手は保留する。実際にアプリを使う中で「見つかりませんでした」が許容できないほど頻繁に出るかどうかを見てから、あらためて着手を判断する
- 対応する要件: docs/requirements.md 3(基本条件の残り)
- 記録: [docs/plans/260829-214939-phase4bスパイク検証.md](./plans/260829-214939-phase4bスパイク検証.md)
