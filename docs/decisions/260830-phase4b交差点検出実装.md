# Phase 4-B: 次数ベースの交差点検出の実装判断

## 背景

Phase 4-Bはスパイク検証（docs/plans/260829-214939-phase4bスパイク検証.md）でGOと判断済み。本実装にあたり、以下の判断を行った。

## 目的地の種類を3択にする

交差点候補は、既存の「店以外」（峠・展望・山頂）の候補プールに混ぜなかった。交差点は仮地点1点の周辺（±1km程度）に局所的に固まるという、峠・展望・山頂（帯全体から均等に出る）とは異質な性質を持つ。混ぜると「同じ店以外なのに実際の挙動が違う」という利用者への裏切りになるため、目的地の種類を「スポット（店）」「スポット（店以外）」「交差点」の3択にした。

表記は当初「POI」も検討したが、既存の周辺情報表示側で既に「スポット」という訳語を使っている（「周辺のスポットを見る」等）ため、アプリ内の用語を揃える意味で「スポット」を採用した。

交差点には詳細条件（停車できる場所、等）を設けていない。負荷が大きいとわかっている検索にさらに条件を足さない判断による。

## 技術設計

### 仮地点と2段階検索

現在地から乱数の方角（0〜360°）×指定距離ちょうど（`radiusKm`）の点を仮地点とする（`src/lib/geo.ts`の`destinationPoint`、順方向の球面測地線計算）。指定距離の帯の内側・外側どこかではなく指定距離ちょうどにしたのは、仮地点自体が帯の端に寄っていると、そこから拡張した際に帯の外にはみ出す候補ばかりになりかねないため。

仮地点の周辺100mで交差点数を診断（プローブ）し、`INTERSECTION_PROBE_MIN_COUNT`（暫定値5件）未満なら1kmまで1回だけ拡張する。拡張後も見つからなければ、それ以上は探さずそのまま0件として返す（既存の帯検索と同じ「無理に見つけようとせず正直に伝える」方針）。

### 交差点判定

Overpass側では交差点判定（関係計算）を行わず、仮地点周辺の道路網（way＋ノード）の生データを取得し、アプリ側でノードの次数（そのノードを共有する異なるway数）を計算する（`src/lib/intersection.ts`の`computeIntersectionCandidates`）。次数3以上のノードを交差点候補とする。この判定は簡易的で、同一道路がタグ上複数wayに分割されているだけのケースを誤検出する可能性がある既知の制限として扱う。

実装中、Overpassの`out geom`で取得した高速道路除外用ジオメトリにも`nodes`フィールドが含まれることが判明し、次数計算に紛れ込む不具合があった。`geometry`フィールドの有無で道路網グラフ用のwayと区別するよう修正した（`destinations.ts`の`candidateElements`/`highwayElements`分離と同じ考え方）。

### prepare/processの多段階化

既存カテゴリは「prepare→（クライアントがOverpassへ直接fetch）→process」の1往復で完結するが、交差点はプローブ→（必要なら）拡張の最大2段階になりうる。`/process`のレスポンス型を`/prepare`と共通化（`ProcessResponseBody = PrepareResponseBody`）し、クライアント側（`public/js/search.js`）を「`need_fetch`が返る限りfetch→processを繰り返す」というループにすることで、両カテゴリに対応した。既存カテゴリは`need_fetch`が最大1回しか返らないため、ループにしても動作は変わらないことを回帰確認済み。

### キャッシュ・再抽選（初版の設計・問題・修正）

**初版の設計（問題あり）**: 既存カテゴリと同じprepare/processのキャッシュパターンをそのまま流用し、キャッシュキーを現在地・探索範囲・カテゴリ（`ov:v3:intersection:...`）でバケット化した。仮地点の乱数決定はキャッシュが空のとき（最初の1回）にしか行わない設計だった。

**発覚した問題**: 実装直後の動作確認で、「トップ画面に戻って検索し直しても、その場で再抽選しても、検索結果地点がほぼ変わらない」という不具合が見つかった。原因は、交差点候補が仮地点1点の周辺（最大1km程度）に局所的に集まる性質を持つのに対し、キャッシュキーが現在地・探索範囲でバケット化されていたため、同じ現在地・探索範囲での検索・再抽選がすべて同じキャッシュバケット（＝同じ仮地点の候補群）を共有してしまい、仮地点の乱数決定が実質24時間に1回しか行われなくなっていたことだった。生成ロジック自体（`Math.random()`の呼び出し）は正しいにもかかわらず、キャッシュ設計とのミスマッチにより外形的には乱数バグに見える不具合が生じた（この教訓はCLAUDE.md「作業の進め方」およびメモリ`cache-key-scope-must-match-variation-source`に一般教訓として記録した）。

**修正後の設計**: 仮地点は検索のたび（再抽選を含む）に必ず新しく引き直す。キャッシュキーは現在地・探索範囲ではなく**仮地点自身の座標**をバケット化したもの（`src/lib/cache.ts`の`buildIntersectionCacheKey`、`int:v1:...`、1km基準・250m四方のバケット）に変更した。これにより、引き直した仮地点がたまたま過去にキャッシュ済みの領域と近ければ再利用され、遠ければ新たにOverpassへ問い合わせる。

キャッシュに保存する内容も、帯フィルタ前（高速道路除外後）の候補に変更した。帯フィルタ（現在地から見て指定の帯に収まっているか）は現在地・探索範囲に依存するため、キャッシュ取得後に毎回その場で適用し直す。これにより、異なる現在地・探索範囲からの検索が同じ仮地点付近のキャッシュを再利用しても正しく動作する。

旧`ov:v3:intersection:...`のキャッシュキーは、この修正によりもう読み書きされなくなった。本番に残っていたエントリ（1件）は手動で削除した。既存カテゴリ（食事・休憩／買い物・その他／店以外）のキャッシュキー（`ov:v3:...`）は変更していない。

詳細は docs/plans/260830-073043-交差点キャッシュを仮地点ベースに変更.md を参照。

### 見つからない・エラー時に画面遷移を強制していた問題

結果画面で「見つかりませんでした」「エラー」になった際、下部シートごと非表示にしており、その場で再検索する手段がなかった。「戻る」を押して条件設定画面に戻り、条件を変えずにもう一度検索すれば同じことができるため、画面遷移を強制する意味がなく動線として分かりにくいという指摘を受け、ステータス表示のその場に「↻ もう一度探す」ボタンを追加した。詳細は docs/plans/260830-074604-見つからなかった時に再検索ボタンを表示.md を参照。

### 仮地点が海上に当たり空振りが頻発する問題

仮地点の方角を`Math.random() * 360`で決めており、陸か海かを一切考慮していなかった。横浜（湾岸）を起点に50km・8方角で実測したところ、8方角中2方角（25%）が海上に着地し、1kmまで拡張しても道路データが一切見つからなかった。`is_in`（行政区画への包含判定）による軽量な陸地事前チェックを検討したが、日本の沿岸自治体は行政区画が海側にも及ぶことが多く、海上の地点も「陸地」と誤判定されることを実測で確認し、採用を見送った。

対応として、1つの仮地点が完全な空振り（プローブ・拡張とも道路データ0件）だった場合、利用者に見せる前に内部で自動的に別の方角の仮地点を引き直すようにした（距離は変えず方角だけ引き直すため、探索範囲を勝手に広げない方針とは矛盾しない）。上限は2回（最大4回のOverpass問い合わせ）とし、それでも見つからなければこれまで通り正直に「見つかりませんでした」と伝える。詳細は docs/plans/260830-075848-交差点仮地点の海上ハズレを内部リトライ.md を参照。

## 検証結果

- 既存カテゴリ（食事・休憩／買い物・その他／店以外）のクエリ・キャッシュキー・動作に変化がないことをcurlで回帰確認した
- 交差点カテゴリで、プローブ→拡張→確定の2段階フローが実際のOverpassデータで正しく動作することを、性質の異なる2地点（郊外、都心近郊）で確認した。いずれも100mプローブでは不足し1kmまで拡張が必要だった（それぞれ134件・156件の交差点候補を検出）
- 実ブラウザ（Playwright）で、キャッシュ済み・未キャッシュ両方のケースで目的地種類の切り替え・検索・再抽選・目的地情報タップでのコピーが正常に動作し、コンソールエラーがないことを確認した

詳細な実装ステップ・実行結果は docs/plans/260830-060923-phase4b交差点検出実装.md を参照。
