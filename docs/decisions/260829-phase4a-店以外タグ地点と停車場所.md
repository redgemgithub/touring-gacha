# Phase 4-A: 目的地種別「店以外」＋停車できる場所条件の実装判断

## 背景

要件4.2「店以外」の目的地種別と、要件3「少なくとも交差点など、地点として区別できる場所を候補とする」の完全な充足が、Phase 1〜3完了時点での残課題だった。

## Phase 4を4-A/4-Bに分割した判断

要件3の「交差点」検出（道路網の次数計算）は、Overpass側で計算すると計算コストが非常に高い（Phase 1で`around.SET`近接フィルタが実際にタイムアウトした前例と同種のリスク、docs/decisions/260829-overpass-client-side-fetch.md参照）。データ量・応答時間の見積もりが取れていない状態で実装に着手するのは避け、以下の2段階に分けた。

- **Phase 4-A（実装済み）**: 峠・展望・山頂といった、Overpassのタグ検索だけで完結する「地点として区別できる場所」＋停車できる場所条件。店舗POIと同じ理由で交差点判定なしに要件3を満たせる
- **Phase 4-B（未実装・設計のみ）**: 次数ベースの交差点検出。curlでの件数・応答時間の事前計測を行い、実用的な待ち時間（目安数秒、10秒超えは要再検討）に収まるか確認してから、着手可否をあらためて相談する

モックアップの「店以外」の例示「峠・展望・道の分岐 等」のうち、「道の分岐」（＝交差点）はPhase 4-Bに送り、Phase 4-Aでは扱わない。

## タグ選定

`src/lib/overpass.ts`の`CATEGORY_TAG_FILTERS.other`:

- `natural=peak`（山頂）
- `natural=saddle`（峠。地域によるタグ付け慣習の違いに対応するため`mountain_pass=yes`と両方指定）
- `mountain_pass=yes`（峠）
- `tourism=viewpoint`（展望）

## 「停車できる場所が必要」＝判断できない候補は除外する

要件4.2「停車可否については、地図データ等から判断可能な場合のみ条件として使用する」の解釈について、ユーザーに確認した。「停車できる場所が必要」を選んだ際、候補近くに駐車場データが単に見つからない（判断できない）場合は、その候補を除外することとした。「判断できないものは通す」ではなく「確実に確認できたものだけ残す」という解釈であり、既存の帯検索の設計思想（見つからなければ無理にひねり出さず正直に伝える、docs/decisions/260829-search-radius-band.md）と一貫させている。

## 停車場所の近接判定バッファ: 実データ検証の末、50m→1000mに変更

当初、店舗カテゴリの高速道路除外バッファ（100m）に近い感覚で`PARKING_PROXIMITY_BUFFER_M=50m`を暫定値としていたが、実装中に実データで検証したところ、事実上機能しないことが判明した。

高尾山周辺（山・峠の多いエリア、探索範囲10km・帯20km相当）でOverpassに実際に問い合わせ、山頂・峠・展望データ（300件）と駐車場データ（300件）の全組み合わせで最短距離を計算した結果:

| 距離しきい値 | 該当候補数（300件中） |
|---|---|
| 50m（当初の暫定値） | 0件 |
| 100m | 0件 |
| 200m | 1件 |
| 300m | 1件 |
| 500m | 5件 |
| 1000m | 32件 |
| 2000m | 71件 |

店舗（建物の出入口に駐車場が隣接することが多い）と異なり、山頂・峠・展望はOSM上のタグ位置が地形の頂点そのものであり、実際の駐車場（登山口・展望駐車場等）はそこから数百m以上離れているのが一般的なため、店舗と同じ50mバッファを流用すると常に候補0件になってしまう。

ユーザーと協議の上、`PARKING_PROXIMITY_BUFFER_M`を**1000m（1km）**に変更した。バイクでツーリング中に「停車できる場所が近くにある」と感じる距離感として、1km以内であれば十分近いという判断による。

## 周辺情報表示（Phase 3）との整合性

上記の変更により、「停車できる場所が必要」で選ばれた目的地は、最大1km離れた駐車場が選定根拠になりうる。一方、既存の周辺情報表示（`src/lib/nearby.ts`、`NEARBY_POI_RADIUS_M=500m`）は駐車場も含めて一律500m圏内しか検索しない。このままだと、選定根拠の駐車場が500m〜1kmの位置にあった場合、周辺情報を開いても駐車場が1件も表示されず「該当なし」に見え、選定根拠と表示が矛盾してしまう。

この矛盾を避けるため、周辺情報取得時、目的地が「店以外」×「停車できる場所が必要」で選ばれた場合に限り、駐車場だけ検索範囲を1kmに広げるようにした（他のPOI種別は従来通り500m）。

「500mで空なら1kmに広げる」という2段階の条件分岐は採用しなかった。周辺情報一覧はもともと距離の近い順に並べて上位`NEARBY_POI_LIMIT`件のみ表示する仕組み（`rankNearbyPois`）のため、駐車場だけ検索範囲を最初から1kmにしておけば、500m以内にあれば自然と上位に、なければ500m〜1kmのものが代わりに表示される。2段階にすると、コードが複雑になるうえOverpassへの問い合わせ回数も増える（無料枠・レート制限の観点で不利）ため、最初から1kmで検索する設計とした。

実装:
- `src/lib/nearby.ts`の`buildNearbyQuery`に、駐車場だけ別半径（1km）で検索する分岐を追加（`parkingWideSearch`引数、既定は偽で既存動作と完全に同一）
- `src/types.ts`の`NearbyPrepareRequestBody`に`parkingWideSearch?: boolean`を追加（クライアントが任意の半径を指定できるとキャッシュキー空間が荒れるため、サーバー側の固定定数を使うON/OFFのフラグのみ渡す設計にした）
- `src/lib/cache.ts`の`buildNearbyCacheKey`に、`parkingWideSearch`が真のときだけ区別用セグメントを付与（既存のキャッシュキーは1バイトも変わらないため`poi:v1`のバージョンは据え置き）
- `src/lib/poi.ts`の`classifyPoiKind`が`amenity=motorcycle_parking`を駐車場として認識していなかった点も、今回の変更に直結するため合わせて修正した（`amenity=parking`と同様に`parking`種別として扱う）

## その他の技術判断

- `ShopCategory`を`DestinationCategory`にリネームし、値に`"other"`を追加した
- 停車場所データ（`amenity=parking`, `amenity=motorcycle_parking`）の取得は、既存の高速道路ジオメトリ取得と同じ「別のOverpass文として同一クエリ内に含める」パターンを踏襲した（候補との近接判定はOverpass側でやらない。高速道路除外時の教訓、docs/decisions/260829-overpass-client-side-fetch.md、を踏襲）
- `category==="other"`のときだけクエリ・キャッシュキーに変更が及び、既存カテゴリ（`food_rest`/`shopping_other`）のクエリ文字列・キャッシュキーは1バイトも変わらないことをcurlで回帰確認した
