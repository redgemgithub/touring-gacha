# KVキャッシュキーのバージョニング原則

## インシデント

探索範囲の帯検索修正（docs/decisions/260829-search-radius-band.md）をPhase 3のデプロイに含めて本番反映した後、「探索範囲50kmを指定したのに、現在地から6.3kmの場所が提示される」という報告があった。

### 原因調査

本番KVのキャッシュキー一覧を確認したところ、`ov:v1:food_rest:50:33.2207:131.6685`というエントリが存在した。中身を取得したところ、検索起点から約6kmの候補が含まれており、帯（45〜55km）でのフィルタが一切かかっていないデータだった。

### 根本原因

- 探索範囲を「円内」から「帯」に変更した際（docs/decisions/260829-search-radius-band.md）、`/api/destinations/process`の候補フィルタリングロジックは変更したが、**KVキャッシュのキー名（`ov:v1:...`の`v1`部分）は変更しなかった**
- そのため、修正前のコード（円内検索、帯フィルタなし）が書き込んだキャッシュエントリが、修正後のコード（帯フィルタあり）からも「有効なキャッシュ」としてそのまま読み込まれ続けた
- キャッシュのTTLは24時間のため、修正をデプロイしてから最大24時間、この状態が起こりうる
- この種の不具合は、コード変更時のtypecheck・E2E確認では検出できない。**E2Eテストは基本的に新規のキャッシュミス→書き込みのパスを通るため、「本番に残っている、修正前のロジックが書き込んだ古いキャッシュ」という状況を再現しない**。ローカル開発環境（`wrangler dev`）のKVも通常テストのたびにクリアしているため、同様に気づきにくい

## 決定: キャッシュキーに含めるバージョン番号は、内容を決めるロジックのバージョンと連動させる

**KVキャッシュのキーに含めるバージョン番号（`ov:v1`, `poi:v1`など）は、「キャッシュに保存する値の中身・意味を決めるロジック」を変更するたびに必ず上げる。** 保存するデータの型（TypeScriptの型定義）が変わらなくても、フィルタ条件など「どの候補が生き残ってキャッシュされるか」が変わるなら、それは内容の意味が変わったことになり、バージョンを上げる対象になる。

判断基準: 「今この関数を直した後に、直す前の呼び出しで書き込まれた既存のキャッシュ値をそのまま読んでも、正しい結果と言えるか？」を自問し、言えないならバージョンを上げる。

### 対象範囲

このプロジェクトの全KVキャッシュに適用する。
- `src/lib/cache.ts`の`buildCacheKey`（目的地候補、`ov:v{N}:...`）
- `src/lib/cache.ts`の`buildNearbyCacheKey`（周辺POI、`poi:v{N}:...`）
- 今後追加されるキャッシュも同様

### この決定に伴う対応

- 今回のインシデントの直接対応として、`buildCacheKey`のバージョンを`v1`→`v2`に上げる（探索範囲帯フィルタの変更に対応するため、本来260829-search-radius-band.md の時点で上げているべきだった）
- 本番KVに残っている`ov:v1:...`の古いキャッシュエントリは、バージョンを上げることで自然に「二度と読まれないキー」になる（削除しなくても実質無害化されるが、ストレージ節約のため明示的に削除もする）
- 実装計画は別途 docs/plans/ に記録する

## 教訓（一般化）

キャッシュキーのバージョン管理は、データ構造（スキーマ）の変更だけでなく、**そのデータを生成する業務ロジックの変更にも連動させる必要がある**。スキーマが同じままロジックだけ変えると、この種の不整合は静かに発生し、テストでは気づきにくい。本番環境で長時間稼働しキャッシュが蓄積するアプリケーションほど、影響が顕在化するまでに時間がかかる（今回は本番稼働から日をまたいでいなかったため早期に発覚したが、稼働期間が長いほど発見が遅れうる）。
